# 📜 Audit Log Service

**A centralized, immutable event log for distributed systems.**

Built as a permanent system of record for events generated by upstream services like **PayFlow** and **Notification Queue** — append-only, queryable, and production-ready.

## 🧭 Why This Exists

Modern backends are made of many small services, and every one of them does *something* worth remembering — a payment fails, a user registers, a notification bounces. Without a single source of truth, that history is scattered across logs, databases, and dashboards that don't talk to each other.

**Audit Log Service** solves that with one simple rule: **once an event is written, it can never be changed or deleted.** It's a dedicated, centralized store that any service in your system can write to and any service (or engineer) can query — reliably, quickly, and with a full historical trail.

---

## ✨ Key Features

| | |
|---|---|
| 🔒 **Append-Only by Design** | No update or delete endpoints exist. Once an event lands, it's permanent — a true audit trail. |
| 🧩 **Schema-Agnostic Payloads** | PostgreSQL `JSONB` metadata means any upstream service can log any shape of data without migrations. |
| 🔍 **Powerful Filtering** | Query by `entityId`, `actor`, `action`, or an ISO-8601 `startDate`–`endDate` time window — in any combination. |
| 📄 **Pagination & Sorting** | Every response is paginated and sorted newest-first, with `totalPages` / `totalElements` metadata baked in. |
| 📊 **Aggregation & Stats** | A dedicated stats endpoint summarizes event volume by type, service, and time window. |
| 🔐 **API Key Authentication** | Ingestion is protected — only trusted services can write new events. |
| 🐳 **One-Command Setup** | A multi-stage Dockerfile and `docker-compose.yml` spin up the app and database together, healthchecks included. |

## 🔌 API Reference

### `POST /api/events`
Validates and persists a new, immutable audit event.

**Headers:** `X-API-Key: <your-key>`

```json
{
  "entityId": "order-8271",
  "actor": "payflow-service",
  "action": "PAYMENT_FAILED",
  "metadata": {
    "amount": 4999,
    "currency": "USD",
    "reason": "insufficient_funds"
  }
}
```

**Response:** `201 Created`

---

### `GET /api/events`
Retrieves paginated, filterable audit logs.

| Query Param | Type | Description |
|---|---|---|
| `entityId` | string | Filter by the affected entity |
| `actor` | string | Filter by who/what triggered the event |
| `action` | string | Filter by event type, e.g. `PAYMENT_FAILED` |
| `startDate` / `endDate` | ISO-8601 | Restrict results to a time window |
| `page` / `size` | int | Pagination controls |

```
GET /api/events?action=PAYMENT_FAILED&startDate=2026-08-01T00:00:00Z&endDate=2026-08-29T00:00:00Z&page=0&size=10
```

---

### `GET /api/events/stats`
Aggregated counts of events, grouped by type, producing service, and time window — useful for dashboards and monitoring.

```
GET /api/events/stats?groupBy=action&startDate=2026-08-01T00:00:00Z&endDate=2026-08-29T00:00:00Z
```

## 🗂️ Schema Highlights

The core `AuditEvent` entity is built to be a trustworthy, tamper-resistant record:

- Auto-generated **UUID** primary keys
- Immutable, **server-set timestamps** — clients can never backdate or spoof event times
- `JSONB` metadata column for arbitrary structured payloads from any producer
- No update or delete repository methods exposed at any layer

## 🧠 Design Decisions

A few deliberate choices worth calling out:

- **No `PUT`/`DELETE` endpoints, anywhere.** This isn't an oversight — it's the whole point. An audit log that can be edited isn't an audit log. Immutability is enforced at the API layer, not just by convention.
- **`JSONB` over rigid columns.** Upstream services evolve independently, and this store shouldn't need a migration every time `PayFlow` adds a new field to its payment events. `JSONB` gives structure where it matters (indexed fields like `entityId`, `actor`, `action`) and flexibility everywhere else.
- **Server-set timestamps only.** Clients never send a timestamp — the server stamps every event on arrival, so the log can't be backdated or replayed out of order.
- **API keys for writes, open reads.** Ingestion is the sensitive operation (anyone with a key can create permanent history), so it's gated. Querying is left open for internal dashboards and tooling to consume freely — this can be tightened further depending on deployment context.

## 🐳 Running Locally

```bash
git clone https://github.com/rdjishnu/audit-log-service.git
cd audit-log-service
docker compose up --build
```

This will:
1. Build the Spring Boot application image
2. Start a PostgreSQL container with a healthcheck and persistent volume
3. Boot `audit-service` automatically once the database is ready

The API will be available at `http://localhost:8080`.
